# Subgraph queries used by the agent

These are the three queries behind `market_stats` and the price suggestion in
`create_ringo`. Endpoint and API key go to the backend by DM, never in the repo.

```
POST <SUBGRAPH_QUERY_URL>
Authorization: Bearer <SUBGRAPH_API_KEY>
```

## Read this before you send a marketId

**`marketId` is `keccak256(ringoId)`, not `ringoId`.** Hash before querying:

```ts
import { keccak256, toUtf8Bytes } from "ethers";
const marketId = keccak256(ringoIdBytes); // the raw bytes, not a utf8 string
```

The contract declares `ringoId` as an `indexed bytes`, and Solidity puts
keccak256(value) in the topic for dynamic types — the plaintext never reaches
the log. It survives in calldata, but every Ringo transaction is an ERC-4337
UserOperation, so `transaction.input` is EntryPoint's `handleOps` and the id
sits nested inside `ops[i].callData`. Keying on anything decoded out of that
gives a different id per transaction, which is a subgraph that looks healthy
and joins nothing.

Passing a raw ringoId returns `null`, which the tool must report as "no data
for that market" — never as zeros.

---

One thing to know before reading them: a subgraph has no `GROUP BY`, no `SUM`
and no `COUNT DISTINCT` at query time. Anything aggregated is either
precomputed into an entity while indexing (that is what `DailyStat` and
`Trader` are for) or folded in the caller. Each query below says which.

---

## 1. Stats for one market

Fully precomputed. Single round trip, no folding.

```graphql
query MarketStats($marketId: ID!) {
  market(id: $marketId) {
    id
    claim
    category
    tags
    status
    outcome
    createdAt
    resolvedAt
    volume        # raw USDC, 6 decimals — divide by 1e6 before showing it
    fills
    participants
    ringos(first: 5, orderBy: timestamp, orderDirection: desc) {
      amountA
      amountB
      timestamp
    }
  }
}
```

```json
{ "marketId": "0x00...aa" }
```

`market` is null for an unknown id — the tool should answer "no data for that
market" rather than reporting zeros, which read as "nobody traded".

## 2. Outcome distribution of resolved markets sharing a tag

Feeds the price suggestion: how comparable markets actually settled.

```graphql
query ResolvedByTag($tag: String!, $first: Int = 200) {
  markets(
    where: { tags_contains: [$tag], status: RESOLVED }
    orderBy: resolvedAt
    orderDirection: desc
    first: $first
  ) {
    id
    claim
    outcome
    volume
    fills
    resolvedAt
  }
}
```

The caller counts outcomes. That is deliberate: the distribution depends on the
tag, and precomputing one entity per tag combination would be a lot of indexing
work for a number the tool can fold over 200 rows in microseconds.

**Blocked: tags are not on chain.** Confirmed by the backend on Sep 7 —
`QuestionCreated(bytes,bytes32)` carries no tags and no claim; tags are
generated by Ringo's AI and live only in Mongo. This query matches nothing and
always will. `tags` only has data if
`QuestionCreated` emits it — see `qcTags` in `src/abi-adapters.ts`. If it does
not, use this instead and let the backend resolve tag → ids:

```graphql
query ResolvedByIds($ids: [ID!]!) {
  markets(where: { id_in: $ids, status: RESOLVED }) {
    id
    outcome
    volume
    fills
    resolvedAt
  }
}
```

Same shape of answer, no contract change. Decide which one before Manuel wires
`market-stats.tool.ts`, because it changes the tool's signature.

## 3. Top traders, last 7 days

`Trader.volume` is lifetime, so it cannot answer a windowed question. This
pulls the window's fills and folds them in the caller:

```graphql
query FillsSince($since: BigInt!, $first: Int = 1000, $skip: Int = 0) {
  ringos(
    where: { timestamp_gte: $since }
    orderBy: timestamp
    orderDirection: desc
    first: $first
    skip: $skip
  ) {
    amountA
    amountB
    timestamp
    userA { id }
    userB { id }
  }
}
```

```json
{ "since": "1757116800", "first": 1000, "skip": 0 }
```

Page until a response comes back with fewer than `first` rows. `skip` caps at
5000 on the hosted service — past that, page by `timestamp_lt` on the oldest
row seen instead.

Add `amountA` to `userA`, `amountB` to `userB`, sort descending, take the top
N.

**If this gets slow**, the fix is a `TraderDay` entity (id `dayId-traderId`,
fields volume/fills) written in `handleRingoCreatedAndFilled`, which turns this
into one sorted query with no folding. Not built yet: it costs an extra entity
write per fill during indexing, and at Ringo's current volume the fold is
cheaper. Revisit if the window ever exceeds a few thousand fills.

## Lifetime totals for the stats page

```graphql
query Lifetime($first: Int = 1000) {
  dailyStats(orderBy: date, orderDirection: desc, first: $first) {
    date
    volume
    fills
    fees
    activeTraders
  }
}
```

Sum `volume` and `fees` across days for the lifetime figures. Do **not** sum
`activeTraders` across days — a trader active on Monday and Tuesday counts in
both. It is a daily distinct count, not an additive one.
